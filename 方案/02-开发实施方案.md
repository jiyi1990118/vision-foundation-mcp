# Vision UI 分析引擎 - 开发实施方案（基于代码现状校准）

> 本方案是对 [`01-vision-ui-analysis-设计方案.md`](./01-vision-ui-analysis-设计方案.md) 的**校准版**。
> 经代码勘验，原方案 UI-2/UI-3 设想的「纯 CV 预处理 + 几何检测器 + Layout Engine + Theme Engine」**已大量存在**，实施起点从"从零构建"修正为"**分层抽象 + 扩展补全**"。
>
> 配套团队设计见 [`03-多Agent协同团队.md`](./03-多Agent协同团队.md)。

## 1. 代码现状勘验结论（校准依据）

### 1.1 已存在的 CV/算法能力（无需重建，直接复用）

| 现有资产 | 位置 | 已实现能力 | 对应原方案 |
|----------|------|-----------|-----------|
| **UI 布局提取器** | `src/core/extractors/ui-layout-extractor.ts`（712 行） | 像素级区域检测（header/sidebar/main/footer/card/nav/table/content）、组件检测（11 类）、文本层级、间距测量、媒体区、layoutType 推断（6 类）——**纯 sharp，无 VLM** | Level-B Layout Engine + 部分 Detector（UI-2 已完成 ~80%） |
| **设计令牌提取器** | `src/core/extractors/design-extractor.ts` | 调色板、颜色角色、暗色模式、对比度——纯 sharp | Theme Engine（UI-3 已完成） |
| **标注检测器** | `src/core/annotation-detector.ts` | 多色像素扫描、连通域、膨胀、框精修——纯 sharp | CV 预处理基础 |
| **关键内容提取器** | `src/core/key-content-extractor.ts` | 几何区域匹配 + OCR 表格重建 | 几何算法基础 |
| **OCR 文本布局** | `buildUiLayout`（`skill-pipeline.ts:882`） | OCR 文本启发式（leftSidebar/mainContent/footerActions） | OCR→布局兜底 |
| **场景提取器族** | `src/core/extractors/{chart,diagram,document,code,form}-extractor.ts` | 各场景专属结构 | 复用 |
| **数据结构** | `src/types/domain.ts`（`UiLayoutBlock`/`VisualRegion`/`UiComponentEntry`/`BBox`） | parse 输出结构 | Layout IR 雏形 |

### 1.2 真实差距（本方案要新建的）

| # | 缺口 | 说明 | 影响 |
|---|------|------|------|
| D1 | **分层 IR 类型** | 当前是扁平 `UiLayoutExtraction`，无 Vision IR / Layout IR / Semantic AST / Codegen IR 四层分离 | 核心资产缺失 |
| D2 | **语义 AST 构建器** | 当前是扁平 regions[]/components[] 数组，无层级化组件树（parent/children 语义树） | 阻塞导出 |
| D3 | **关系引擎** | `VisualRegion.children: string[]` 存在但未构成完整父子树；无文字-组件-容器归属 | 布局准确率 |
| D4 | **约束引擎** | 有 `layoutType` 但无 Flex/Grid/响应式约束 | 阻塞 Codegen |
| D5 | **导出器** | 无 Codegen IR / Figma JSON / Markdown 导出 | 终端价值 |
| D6 | **插件接口统一** | 检测/提取器是单体函数，无 `Detector`/`Segmenter`/`Exporter` 统一 Trait | 可扩展性 |
| D7 | **组件类型覆盖** | 现有 11 类，目标 30+ 类（含 IconButton/Avatar/Switch/Tab/Dialog 等） | 精度 |
| D8 | **排版引擎** | 有 `estimatedLevel`，无完整字号 scale / 字重 / 行高推断 | 主题完整性 |

### 1.3 关键约束（来自 AGENTS.md）

- `pnpm build` 会拷贝 `src/skills/*/{skill.json,prompt.md,schema.json}` 到 `dist/skills/`，新增 Skill 必须含三件套。
- 日志必须走 stderr（MCP stdio）。
- `pnpm typecheck` + `pnpm test:unit` 必须始终绿。
- 现有 `vision.analyze` 契约不可破坏（向后兼容 M1–M8）。

## 2. 校准后的实施策略

### 2.1 核心策略：分层抽象，不动存量

```
                现有单体提取器                         新增分层 IR + 引擎 + 导出
   ui-layout-extractor ──┐                    ┌──> Vision IR  (原始事实)
   design-extractor ─────┼── 适配器(薄) ──────┤──> Layout IR  (几何布局)
   annotation-detector ──┘                    └──> Semantic AST (语义树) ──> Codegen IR
                                                                    │
                                                              Exporter (Figma/React-IR/MD)
```

- **不重写** `ui-layout-extractor.ts` / `design-extractor.ts`，而是在其上包一层**适配器**，将其输出映射为分层 IR。
- 现有 `result.parse.uiLayout` 字段**保留**（向后兼容），新 IR 写入 `result.ui` / `result.codegenIr`。
- 插件接口在 IR 稳定后，反向重构存量提取器去实现统一 Trait（**最后做**，低优先）。

### 2.2 IR 冻结优先（Interface-First）

D1（分层 IR）是所有引擎/导出的契约前置，**必须最先冻结**，否则下游并行会返工。这是多 Agent 并行的关键。

## 4. 分阶段交付（Wave）

### Wave 1 — 契约冻结（关键路径，无依赖）

**S0：四层 IR 类型 + Schema**

交付物：
- `src/ui-analysis/ir/types.ts`：四层 IR 类型定义
  - `VisionIR`：原始检测框 `{ type, bbox, score }[]`、OCR 文本框 `{ text, bbox, confidence }[]`、Mask、颜色采样
  - `LayoutIR`：对齐组、间距、padding、`{ regions, layoutType, spacing }`（**对齐**现有 `UiLayoutExtraction.structure`）
  - `SemanticAST`：层级化组件树节点 `{ id, type, bbox, props, children: ASTNode[] }`，类型枚举 30+ 类（D7）
  - `CodegenIR`：框架无关描述 `{ root, constraints, responsive, slots, repeats }`
- `src/ui-analysis/ir/mappers.ts`：现有 `UiLayoutExtraction` / `DesignExtraction` → `VisionIR`/`LayoutIR` 的薄适配器
- `src/ui-analysis/ir/schema/{vision_ir,layout_ir,semantic_ast,codegen_ir}.schema.json`

**S6：外部调研（并行）**
- Figma JSON 节点结构规范（供 S3 Figma 导出对齐）
- YOLOv11 / RT-DETR 基于 Rico 数据集微调的可行性、模型体积、GPU 依赖（供 UI-6 决策）
- SAM2 / GroundingDINO 集成成本评估

验收：
- `pnpm typecheck` 通过；新文件不破坏现有类型
- IR 类型可独立 import；mapper 单测覆盖 `UiLayoutExtraction → VisionIR`
- S6 产出 `方案/调研-note.md`

**执行 Agent**：契约 Agent（S0）+ 调研 Agent（S6，并行）

---

### Wave 2 — 引擎与插件化（依赖 S0）

**S1：引擎层**
- `src/ui-analysis/ast/ast-builder.ts`：`LayoutIR → SemanticAST`（扁平数组转层级树，含父子包含、文字归属）
- `src/ui-analysis/relationship/`：父子包含算法（bbox 包含 + 对齐聚类）、文字-组件-容器归属
- `src/ui-analysis/constraint/`：行/列/Grid/Flex 约束生成（基于现有 `layoutType` + 间距）
- `src/ui-analysis/typography/`：字号 scale / 字重推断（基于 OCR bbox 高度聚类）

**S2：插件化重构（与 S1 并行）**
- `src/ui-analysis/plugin/types.ts`：`Detector` / `OcrEngine` / `Segmenter` / `LayoutEngine` / `AstBuilder` / `Exporter` 接口
- 现有 `ui-layout-extractor` / `design-extractor` 包一层实现 `LayoutEngine`/`Detector`（**不改原函数**，加适配类）

验收：
- `LayoutIR → SemanticAST` 单测：给定扁平 regions/components 输出含层级的树
- 约束引擎输出可被下游渲染的 `{direction, gap, align}` 结构
- `pnpm typecheck` + `pnpm test:unit` 绿

**执行 Agent**：引擎 Agent（S1）+ 重构 Agent（S2，并行）

---

### Wave 3 — 导出与集成（依赖 S1/S2）

**S3：导出层**
- `exporter/codegen-exporter.ts`：`SemanticAST → CodegenIR`
- `exporter/figma-exporter.ts`：`SemanticAST → Figma JSON`（对齐 S6 调研结论）
- `exporter/markdown-exporter.ts`：`SemanticAST → 可读文档`

**S4：集成层**
- `src/skills/analyze-ui/{skill.json,prompt.md,schema.json}`（三件套，`pnpm build` 会拷贝）
- `src/tools/vision-analyze.ts`：`scene ∈ {ui, prototype}` 时触发 UI 流水线，结果写入 `result.ui` / `result.codegenIr`；保留 `result.parse.uiLayout` 向后兼容
- `options` 扩展：`detect_layout / detect_component / build_tree / use_llm / strict_mode`
- `use_llm:false` 时全程零 VLM 推理（除 OCR）

验收：
- `vision.analyze({ image, scene: "ui", options: { build_tree: true } })` 返回 `result.ui.components[]` 层级树
- 现有 M7/M8 测试全绿（向后兼容）
- Figma JSON 结构合法（S6 规范校验）

**执行 Agent**：导出 Agent（S3）→ 集成 Agent（S4）

---

### Wave 4 — 质量与可选升级

**S5：质量层**
- `tests/ui-analysis/*.test.ts`：IR mapper / AST builder / constraint / exporter 单测
- `scripts/ui-benchmark.ts`：准确率/延迟/内存/确定性度量（对齐现有 `scripts/benchmark.ts`）
- 回归：确保 `result.parse.uiLayout` 与新 `result.ui` 一致性

**UI-6（可选）**：基于 S6 调研接入 YOLO 检测器（GPU 可用时），否则回退 Level-B

验收：
- Benchmark 达标（组件 Precision ≥ 0.8，端到端 < 500ms，确定性 diff = 0）
- `pnpm test:unit` 全绿

**执行 Agent**：质量 Agent（S5）

## 5. 关键设计决策（更新 R 表）

| # | 决策 | 校准后结论 |
|---|------|-----------|
| R1 | OpenCV 依赖 | **已解决**：`sharp` 已被 `ui-layout-extractor`/`annotation-detector` 使用并批准，继续用 sharp |
| R2 | 是否引入 YOLO | v1 不引入（Level-B 已可用）；S6 调研后由 UI-6 决策，可选 |
| R3 | IR 与现有 `uiLayout` 共存 | 新 IR 写 `result.ui`；`result.parse.uiLayout` 保留并标注 deprecated-but-stable |
| R4 | 是否拆独立 MCP 工具 | v1 不拆，保持 `vision.analyze` + options；Spec 阶段再拆 |
| R5 | LLM 增强默认值 | `use_llm` 默认 `false` |
| R7 | 存量提取器是否重写 | **不重写**，加薄适配器映射为 IR；插件化在 S2 反向适配，最低优先 |
| R8 | `buildUiLayout`（skill-pipeline OCR 启发式）与 `extractUiLayout`（像素级）关系 | 二者并存：像素级为 Layout IR 主源；OCR 启发式作为语义补强（表头/行值识别）喂入 Relationship Engine |

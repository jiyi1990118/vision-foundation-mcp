# "UI -> 代码" 目标专项分析与实现度评估

> 本文档基于 [`设计沟通.md`](../设计沟通.md) 重新聚焦于一个明确目标：**做一个类似 Cursor / Claude Code 的 "UI 截图 -> 可用代码" MCP 工具**。
> 在此前 [`01-设计方案`](./01-vision-ui-analysis-设计方案.md) / [`02-开发实施方案`](./02-开发实施方案.md)（通用 UI 分析引擎）之上，本文件针对"代码生成"目标做收敛分析与实现度评估。

---

## 1. 设计沟通.md 对"UI->代码"的核心命题

### 1.1 关键论断（设计沟通 §"如果你的目标是做一个类似 Cursor / Claude Code 的 UI->代码 工具"）

设计沟通明确：**混合方案**，且给出了能力-方案-是否需LLM 的对照表：

| 能力 | 推荐方案 | 是否需要 LLM |
|------|---------|-------------|
| UI 元素检测 | YOLO / RT-DETR | ❌ |
| 文字识别 | PaddleOCR | ❌ |
| 图标检测 | GroundingDINO / YOLO | ❌ |
| 布局分析 | OpenCV + 几何规则 | ❌ |
| 自动约束（行/列/Grid/Flex） | 几何算法 + 图算法 | ❌（大部分） |
| 组件识别（Button/Card/Input） | UI 检测模型 | ❌ |
| 页面类型判断（登录/订单/设置） | 轻量分类模型或 LLM | 可选 |
| **生成 React/Vue/Flutter 代码** | **规则引擎 + 模板，复杂场景结合 LLM** | **可选** |
| 代码重构、变量命名、业务语义理解 | LLM | ✅ |

### 1.2 核心架构（设计沟通推荐）

```
UI截图
  -> OpenCV轮廓检测
  -> YOLO检测UI组件
  -> PaddleOCR文字
  -> 组件关系重建(Layout Tree)
  -> JSON AST（UI结构）
  -> ┌ 直接生成代码(Vue/React等)
     └ 交给LLM分析(页面语义、优化建议)
```

关键洞察（设计沟通原话提炼）：
> **CV 负责"看见"，LLM 负责"理解"。90% 的工作不需要 LLM。**
> Code Generator **不用分析图片**，直接消费 Codegen IR。

### 1.3 IR 分层（设计沟通 §"统一 IR 是最值钱的地方"）

```
Raw Vision IR -> Layout IR -> Semantic AST -> Design Token -> Codegen IR -> React / Vue / Flutter / Compose / MiniProgram
```

设计沟通强调：**Codegen IR 是分水岭**--它之前全是确定性算法，之后才是框架代码（可选 LLM）。这条分层正是"UI->代码"工具能否做到快、稳、便宜的关键。

## 2. 最合适方案：两段式混合架构（收敛设计）

针对"UI->代码"目标，把设计沟通的混合方案落地为**两段式**：

```
┌─────────────────────────────────────────────────────────────┐
│  Stage 1  确定性感知层（无 LLM，快/稳/便宜/可缓存）           │
│  截图 -> VisionIR -> LayoutIR -> SemanticAST -> CodegenIR    │
│  产出：结构化、确定、可复现的 CodegenIR（框架无关）           │
└──────────────────────────┬──────────────────────────────────┘
                           │ CodegenIR + AST + uiSemantics
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  Stage 2  代码生成层                                          │
│  2a 模板发射器（无 LLM）：CodegenIR -> React/Vue/HTML 骨架    │
│     - 组件类型 -> 框架组件 + 库映射（AntD/MUI/Tailwind）       │
│     - constraints -> flex/grid 样式                          │
│     - theme -> CSS 变量 / Tailwind token                     │
│  2b LLM 增强（可选）：骨架 + AST -> LLM                      │
│     - 变量命名 / 业务语义 / 事件处理器 / 数据模型 / 重构       │
│     - use_llm=true 时触发；默认 false 出纯模板骨架            │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 为什么是这个方案

1. **契合设计沟通**：完全对应"规则引擎+模板，复杂场景结合 LLM"+ "Code Generator 直接消费 Codegen IR"。
2. **Stage 1 已基本建成**（见 §3）：无需重做感知层，直接复用现有 IR/AST/约束/语义引擎。
3. **LLM 真正可选**：默认走 2a 纯模板（0 模型、毫秒级、确定），2b 仅在 `use_llm=true` 时增强--这正是 Cursor/Claude Code 类工具的"快路径 + 慢路径"分治。
4. **降低幻觉风险**：LLM 消费的是结构化 CodegenIR（坐标/类型/约束已知），而非原始图片，命名/语义错误可控、可回退到模板。

### 2.2 与通用方案（01/02）的差异

| 维度 | 通用 UI 分析方案（01/02） | UI->代码 收敛方案（本文件） |
|------|------------------------|-------------------------|
| 终点 | UI AST + 多端导出（含 CodegenIR） | **可运行框架代码** |
| CodegenIR | 最终产物之一 | **中间桥梁**（喂给代码发射器） |
| use_llm | 标志，不实现 | **2b 真实接入 VLM/LLM** |
| 组件库 | 不感知 | **必须映射到真实 UI 库** |
| 优先级 | 均衡 | **代码发射器 + 库映射为 P0** |

| 12 | 代码重构/命名/业务语义 | LLM | **未实现** | 🔴 **缺失（P0）** |
| 13 | 组件库映射 | - | **未实现**（AST type 是抽象类型，未映射到 AntD/MUI/Tailwind） | 🔴 **缺失（P0）** |
| 14 | 响应式/条件逻辑 | 算法+LLM | `CodegenIR.responsive` 字段存在但 **omit 未填**；`slots`/`repeats` 空数组 | 🔴 **缺失（P1）** |
| 15 | 重复项/列表检测 | 图算法 | `CodegenIR.repeats` 空数组，无重复检测 | 🟡 **缺口（P1）** |

### 实现度汇总

| 层 | 范围 | 实现度 |
|----|------|--------|
| **Stage 1 确定性感知层**（能力 1–10） | 截图 -> CodegenIR | 🟢 **~90%**（仅 YOLO 级检测与重复项检测缺，Level-B 已满足生产） |
| **Stage 2 代码生成层**（能力 11–15） | CodegenIR -> 框架代码 | 🔴 **~10%**（仅 CodegenIR 桥梁存在；无代码发射、无库映射、LLM 未接） |
| **整体"UI->代码"目标** | 截图 -> 可用代码 | 🟡 **~55%**（地基完成，"最后一公里"代码生成未做） |

> 结论：**确定性地基已夯实，缺的是"CodegenIR -> 可运行代码"这一段**。这恰好是设计沟通反复强调的"LLM 只在这一段介入"的部分。

## 4. 差距分析（按优先级）

### P0 - 阻塞目标的核心缺口

**G1 代码发射器（Code Emitter）**
- 现状：`codegen-exporter` 只投影为 CodegenIR，无任何框架代码输出。
- 需要：`exporter/{react,vue,html}-emitter.ts`，CodegenIR -> JSX / SFC / HTML+CSS 骨架（纯模板，无 LLM）。
- 这是"UI->代码"工具的**交付物**，没有它目标不成立。

**G2 组件库映射（Component Library Mapping）**
- 现状：AST `type` 是抽象（`button`/`input`/`card`），无目标库。
- 需要：`codegen/library-mapper.ts`，把抽象 type + variant + theme -> 真实库组件 + props（如 `button`+`primary` -> AntD `<Button type="primary">` 或 Tailwind class）。
- 否则生成的代码是无样式的裸标签，不可用。

**G3 use_llm 真实接入（LLM 增强路径）**
- 现状：`use_llm` 标志存在但什么都不做。
- 需要：`codegen/llm-enhancer.ts`，`use_llm=true` 时把 CodegenIR + AST + uiSemantics 交给 VLM/LLM，产出命名/事件处理器/数据模型/业务注释。
- 这是 Cursor/Claude Code 类工具的"慢路径"差异化能力。

### P1 - 代码质量与完整性

**G4 响应式与约束填充**
- 现状：`CodegenIR.responsive` omit，`slots`/`repeats` 空数组。
- 需要：`constraint/responsive-engine.ts`（断点推断）+ `repeats` 检测（同构列表项）+ `slots`（可复用区域提取）。

**G5 样式提取**
- 现状：theme 在 LayoutIR 但未进入代码。
- 需要：发射器把 `theme` -> CSS 变量 / Tailwind config / design token 文件。

**G6 代码后处理**
- 需要：变量命名规范化、TypeScript 类型推断、import 整理、格式化（prettier）。

### P2 - 精度提升（可选）

**G7 YOLO 检测模型**（UI-6，S6 已论证 GPU-gated 默认关）
**G8 GroundingDINO 零样本图标检测**（S6 不推荐 v1）

## 5. 下一步路线（"UI->代码"专项）

```
Wave 6  代码发射骨架（P0，解锁目标）
  ├─ S11 组件库映射层（library-mapper：抽象 type+variant+theme -> AntD/MUI/Tailwind 组件+props）
  ├─ S12 React/HTML 发射器（CodegenIR + 库映射 -> JSX/HTML+CSS 骨架，纯模板无 LLM）
  └─ S13 options 扩展（target_framework: react/vue/html/flutter, component_library: antd/mui/tailwind/none）
        交付：vision.analyze({scene:ui, options:{export_codegen:true, target_framework:'react', component_library:'antd'}})
              -> result.code = { files: [{path, content}], framework, library }
        验收：登录截图 -> 可运行的 AntD React 组件骨架（结构正确、样式近似）

Wave 7  LLM 增强路径（P0，差异化）
  └─ S14 llm-enhancer：use_llm=true 时 VLM 消费 CodegenIR+AST+uiSemantics
        -> 变量命名 / onClick 处理器 / 数据模型 / 业务注释
        交付：use_llm=true 出增强代码；false 出纯模板骨架（回退保证）

Wave 8  代码质量与完整性（P1）
  ├─ S15 响应式 + repeats + slots 填充
  ├─ S16 样式提取（theme -> CSS 变量 / Tailwind token）
  └─ S17 后处理（命名规范 / 类型推断 / prettier 格式化）

Wave 9  端到端验收（P1）
  └─ S18 基准集：N 张真实 UI 截图 -> 生成代码 -> 人工/LLM 评分（结构正确率 / 库映射正确率 / 可运行率）
```

### 优先级原则（对齐设计沟通"先跑通>完整"）
1. **Wave 6 是分水岭**：完成后"UI->代码"目标正式成立（哪怕只是骨架）。
2. **先纯模板（2a）后 LLM（2b）**：保证默认路径快/稳/确定，LLM 仅增强。
3. **库映射优先于精度**：可用的 AntD 骨架比高精度裸标签更有价值。

## 6. 结论

- **设计沟通的混合方案完全适用**于"UI->代码"目标，且其分层（到 CodegenIR 为止确定性、之后可选 LLM）是正确的工程边界。
- **当前 MCP 的 Stage 1（确定性感知）已 ~90% 完成**，质量经 review + 端到端验证 + benchmark 确认（延迟 0.03ms、确定性 100%、零回归）。
- **缺口集中在 Stage 2**：无代码发射、无组件库映射、`use_llm` 空壳。这是"UI->代码"从"分析引擎"升级为"代码生成工具"的**最后一公里**。
- **整体实现度约 55%**：地基扎实，差"CodegenIR -> 可运行代码"这一段。
- **建议立即推进 Wave 6**（代码发射骨架 + 库映射），完成后目标即成立；Wave 7 接入 LLM 增强形成差异化。

我认为经过我们这几轮讨论，这个项目已经不再是一个简单的 **Vision MCP**，而是一个**可扩展的本地视觉推理平台（Vision Intelligence Engine）**。

它的目标不是"封装一个视觉模型"，而是**为整个 MCP 生态提供统一、可插拔、高性能、CPU 友好的视觉能力**。

如果由我负责这个项目，我会按照下面这套架构来设计。它既能满足你目前 **SmolVLM-500M Q4_K_M** 的定位，也为未来接入更大的本地模型（如 Qwen2.5-VL、MiniCPM-V）或云端模型预留了扩展空间。

------

# 一、项目定位（Project Vision）

## 核心定位

> 一个专注于视觉理解（Vision Understanding）的 MCP 服务，不负责数据获取，仅负责图片分析与结构化输出。

### 不负责

- Browser 自动化
- Playwright 控制
- HTML 解析
- Search
- URL 抓取
- PDF 下载
- Office 文档读取
- 文件扫描

这些能力交给其他 MCP（Browser MCP、Filesystem MCP、Search MCP 等）。

### 只负责

输入：

```text
Image / Screenshot / Base64 / File
```

输出：

```text
Structured JSON + Text Summary
```

整个 MCP 的职责只有一句话：

> **把图片转换成 AI 可消费的结构化信息。**

    when:

    when:

# 十七、为了让本地模型（SmolVLM-500M Q4_K_M）执行得更准确，我建议增加三层"质量保障"

这是很多本地 AI 项目容易忽略，但实际上决定最终效果的关键。

## 1. Prompt Compiler（提示词编译器）

不要直接把用户问题发给模型，而是将用户意图编译成**针对 SmolVLM 优化的 Prompt**。

例如：

用户："这个页面是什么风格？"

内部转换为：

```text
You are a UI design expert.

Analyze the screenshot.

Return ONLY valid JSON.

Fields:
- design_style
- color_theme
- layout
- typography
- spacing
- components

Do not explain.
Do not output Markdown.
```

不同 Skill 都有自己的 Prompt Template 和 Few-shot 示例。

------

## 2. Response Validator（响应校验器）

本地小模型容易：

- JSON 不完整
- 字段缺失
- 类型错误
- 输出 Markdown

因此每个 Skill 执行后都经过：

```text
Model Output
      │
      ▼
JSON Parse
      │
      ▼
JSON Schema Validate
      │
      ▼
Auto Repair（必要时）
      │
      ▼
Standard Output
```

必要时可进行一次轻量重试，而不是直接把错误返回给用户。

------

## 3. Result Composer（结果组合器）

很多分析不是一次完成，而是多个 Skill 的组合，例如：

```
Auto Analyze
    │
    ├── classify
    ├── ocr
    ├── ui
    ├── color
    └── summary
```

最后由 **Result Composer** 合并为统一的 `structuredContent`，避免各 Skill 输出格式不一致。

------

## 最终目标

我建议把整个项目定位为：

> **一个面向 MCP 生态的、以本地模型为核心、具备 Planner + Policy + Skill + Provider 四层解耦能力的 Vision Intelligence Engine。**

其中 **SmolVLM-500M Q4_K_M** 是默认执行引擎，而 **Execution Planner、Policy Engine、Prompt Compiler、Skill Engine** 才是真正决定准确率、可扩展性和产品竞争力的核心。这样未来无论替换模型还是增加新的视觉能力，都几乎不需要修改整体架构。

# ADR-005: 模型资源释放策略

- **状态**：Accepted（历史决策；当前实现中 SmolVLM-500M 已替换为 SmolVLM2-500M-Video 约 500MB，MiniCPM-V 约 2-3GB，生命周期逻辑内嵌于各 Provider 而非独立模块）
- **日期**：2025-06-30

## 背景

SmolVLM-500M Q4_K_M 加载后占用约 800MB-1GB 内存。必须设计资源自动释放机制，平衡三个矛盾诉求：

1. **内存释放** —— 800MB 在 8GB 机器上占 10%，空闲时应释放
2. **响应速度** —— 模型加载需 2-5 秒，频繁卸载导致用户等待
3. **资源安全** —— ONNX 原生资源必须显式释放，否则泄漏

## 决策

采用**按需加载 + 空闲超时卸载 + 内存压力触发 + 引用计数保护**的组合策略。

### 决策 1：启动不预加载，按需加载

```
启动时：不加载任何模型（零内存）
首次调用：自动加载
```

**理由**：MCP 服务可能长时间空闲，预加载 800MB 浪费资源。按需加载让内存占用与实际使用对齐。

### 决策 2：空闲超时 10 分钟卸载

```
refCount == 0 后 10 分钟无新请求 → unload()
```

**为什么 10 分钟（而非 1 分钟或 30 分钟）**：
- **1 分钟太短**：用户连续操作间隔常超过 1 分钟，导致频繁重载（每次等 2-5 秒）
- **30 分钟太长**：30 分钟内系统可能需要这 800MB 内存做别的事
- **10 分钟是平衡点**：覆盖典型「连续分析多张图」的工作流（通常几分钟内完成），又不会长时间占用

**可配置**：用户可根据自身机器内存调整 `config/lifecycle.yaml` 的 `idleTimeout`。

### 决策 3：最小驻留时间 60 秒（防抖动）

```
加载后即使立即空闲，也至少驻留 60 秒才允许卸载
```

**理由**：避免「加载 → 立即空闲 → 卸载 → 又请求 → 再加载」的抖动。60 秒覆盖单次分析会话的典型时长。

### 决策 4：引用计数保护推理中不卸载

```
acquire() → refCount++
release() → refCount--
refCount > 0 时禁止卸载
```

**理由**：推理中卸载会导致崩溃。引用计数是并发安全的最简方案。

### 决策 5：内存压力主动释放

```
可用内存 < 2GB → 卸载空闲模型
可用内存 < 1GB → 拒绝新请求
```

**理由**：空闲超时是「被动等待」，内存压力是「主动防御」。两者互补，防 OOM。

### 决策 6：6 状态完整状态机

```
Unloaded → Loading → Loaded → Idle → Unloading → Unloaded
                          ↓               ↑
                      Error ──────────────┘
```

**为什么不用简单 3 状态**：3 状态无法处理「加载中被请求卸载」「卸载中被请求推理」等竞态，会导致状态不一致。6 状态覆盖所有转换路径。

### 决策 7：进程退出信号清理

```
SIGTERM/SIGINT → 等待推理完成 → 卸载所有模型 → 退出
```

**理由**：虽然进程退出后 OS 会回收内存，但 ONNX 原生资源可能未正确释放（尤其在某些平台）。显式清理更安全。

### 决策 8：预热（Warmup）

```
加载后执行一次空推理，再标记为 Loaded
```

**理由**：首次推理比后续慢（含编译/优化）。预热把延迟移到加载阶段，让真实推理请求不受影响。

## 替代方案

### 方案 B：模型常驻不卸载
- 优点：零冷启动延迟
- 缺点：800MB 永久占用，低配机器不可接受
- **否决**：违背「本地优先、CPU 友好」原则

### 方案 C：每次请求加载/卸载
- 优点：内存占用最小
- 缺点：每次请求等 2-5 秒加载，体验极差
- **否决**

### 方案 D：固定时间窗口加载（如每天 9-18 点常驻）
- 优点：工作时间无冷启动
- 缺点：假设使用模式，不灵活
- **否决**：不如空闲超时自适应

### 方案 E：仅靠 OS 兜底（不主动释放）
- 优点：实现最简
- 缺点：800MB 长期占用；ONNX 原生资源可能泄漏；无法应对内存压力
- **否决**

## 影响

- 新增 `LifecycleManager` 模块（L6 基础设施层）
- Provider 需实现 `load()/unload()/isLoaded()`，且 `unload()` 必须调用 `session.release()`
- Skill Pipeline 通过 `acquire()/release()` 使用 Provider（try...finally）
- Policy Engine 的 memory-guard 策略联动 LifecycleManager
- 新增 `config/lifecycle.yaml` 配置
- 进程需注册 SIGTERM/SIGINT hook
- 暴露监控指标（provider_state/refcount/memory 等）
